I'm a QA Lead transitioning into SDET, with 3 years testing gaming, web, mobile and streaming platforms for Adobe, Disney+, ESPN, Vix (Televisa Univision), the LA Clippers and Jerónimo Martins. At Electronic Arts I act as an Automation POC — driving automation strategy, improving workflows, and supporting distributed execution environments.

I care about making testing faster and more reliable: cutting manual effort, hardening pipelines, and building frameworks that stay green. Right now I'm going deep on hands-on automation with Playwright and Appium, including where AI genuinely helps and where it doesn't.

My position on that: a framework that silently heals a broken locator has not fixed the test, it has deleted the report. So in my mobile framework healing keeps a run alive but is booked as debt — every rescue recorded with its evidence, and unaccepted debt fails the build. Same reasoning I apply to flaky tests, which carry an expiry date rather than a retry count.

Things I've built.

📱 appium-java-mobile-automation

Java

A cross-platform mobile framework — Appium 3 · Java 21 · JUnit 6 — where one test runs on Android and iOS with no if (isAndroid()) in it. Device pool with per-slot port isolation, in-place app upgrade testing, performance budgets, an accessibility audit, and visual regression. Six CI lanes, including two Android API levels and a real iOS simulator.

Its argument is that flakiness is debt, not a retry setting: quarantined tests carry an expiry date and fail the build once it passes. The optional AI layer follows the same rule — it can rescue a broken locator to keep a run alive, but every rescue is recorded and unaccepted debt fails the build. A CI job deletes the whole AI module and runs the suite without it, so "optional" is enforced rather than claimed.

The same habit applied to a slow, intermittently red iOS lane. Rather than tuning capabilities and hoping, I read the session timings out of the Appium log: the first session cost 432s against a 420s client timeout — twelve seconds, which is why it failed some runs and not others — and session setup turned out to be 63% of the entire lane. The ceiling was raised against the measurement rather than against arithmetic, and the cold start moved into a named warm-up step that verifies its own work.

🧪 restassured-automation

Java

REST Assured · Cucumber 7 · JUnit Platform against an API the suite starts itself — Postgres and PostgREST in Testcontainers. ./mvnw test and nothing else: no API key, no account, no hosted sandbox to go stale. It replaced a suite pointed at a shared mock, which had filled to its row cap and been failing on Max number of elements reached ever since.

A real database means the negative tests assert real behaviour — 23505 on a duplicate email, 23514 on a failed CHECK, and a genuine race where two writers contend for one unique index and exactly one loses.

Its argument is that a negative test nobody has watched fail proves nothing. A CI job re-runs the whole suite against a deliberately weakened schema and requires every assertion on a checked-in list to go red. Writing that list down is what showed the real coverage was five of nine negative scenarios, not nine of nine — and two of the remainder are documented as not coverable this way rather than quietly counted.
